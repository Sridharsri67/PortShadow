# 🔒 Security & Correctness Policy — PortShadow

This document outlines the security invariants, threat model, state mutation protection rules, and environment isolation policies governing **PortShadow**.

---

## 1. Core Correctness Invariant

> **PRIMARY INVARIANT:**
> A packet belonging to an earlier connection incarnation must **never** modify the state of an active connection incarnation.

---

## 2. Threat Model: Transport Port Reuse & Connection Cross-Contamination

### The Vulnerability Scenario
High-throughput systems (such as proxy clusters, microservice meshes, or load balancers) cycle through ephemeral ports rapidly. When Connection A closes and Connection B binds to the exact same 4-tuple:

$$\text{4-Tuple} = (\text{sourceIp}, \text{sourcePort}, \text{destinationIp}, \text{destinationPort})$$

Packets generated by Connection A that were delayed in network routers will arrive at Connection B. Without incarnation validation, these delayed packets appear superficially valid because their 4-tuple matches Connection B's socket.

### Security Impacts of Unvalidated Stale Packets
1. **Data Corruption**: Stale payload bytes inserted into new application stream.
2. **State Desynchronization**: Stale sequence numbers corrupting transport receiver sequence windows.
3. **Session Hijacking Risk**: Inadvertently interpreting delayed command packets from a previous user session as commands for a new user session.

---

## 3. Stale State Mutation Prevention Rules

To enforce strict isolation, PortShadow mandates the following core implementation rules:

1. **Validation Before Mutation**:
   Validation checks MUST occur before any state mutation:
   ```javascript
   // INCORRECT (State mutated before check):
   connection.sequenceNumber = packet.sequenceNumber;
   if (packet.incarnationId !== connection.incarnationId) return REJECT;

   // CORRECT (Validation first):
   if (packet.incarnationId !== connection.incarnationId) {
     logAuditMetric("STALE_INCARNATION_REJECTED", packet);
     return { status: "REJECTED", reason: "STALE_INCARNATION" };
   }
   connection.sequenceNumber = packet.sequenceNumber;
   ```

2. **Immutable Receiver Buffers**:
   A rejected stale packet MUST NOT alter:
   - Receive sequence windows
   - Out-of-order reorder buffers
   - Retransmission timers
   - Application layer payload accumulators

3. **Independent Tombstone Retention**:
   Closing a connection MUST remove it from active transport maps while preserving a tombstone audit record.

---

## 4. Environment & Credentials Security Policy

1. **Modular Environment Isolation**:
   - Backend secrets and system ports are maintained exclusively in `server/.env`.
   - Frontend variables are maintained exclusively in `client/.env` using the `VITE_` prefix.
   - Root-level `.env` files are prohibited to prevent credential leaks between workspaces.

2. **Source Control Safeguards**:
   - `.env` files are strictly listed in `.gitignore` files.
   - `.env.example` templates contain default dummy values only.

---

## 5. Cloud Deployment Security Policy (Vercel, Render, Neon DB)

1. **Frontend Transport Security (Vercel)**:
   - All client-to-backend communication is enforced via TLS (HTTPS / WSS).
   - API Proxy rewrites in [`vercel.json`](file:///Users/sridharkonda/Documents/PortShadow/vercel.json) enforce origin checks and prevent mixed-content warnings.

2. **Backend & WebSocket Gateway Security (Render)**:
   - CORS policy explicitly restricts accepted origins to the verified Vercel frontend domain (`CLIENT_URL`).
   - WebSockets enforce strict handshake origins.

3. **Database Transit Security (Neon DB)**:
   - Neon PostgreSQL connections strictly require TLS/SSL encryption (`sslmode=require`).
   - Database credentials (`DATABASE_URL`) are injected via Render environment variables and never logged or exposed to the client.
